Shiptivitas: daily active users and status changes

Data: shiptivity.db, 3 Feb 2018 to 1 Feb 2019 (100 users, 200 cards). Launch date = first real status change, 28 Jun 2018.

Summary
  • Average daily active users went from 5.0 before launch to 11.7 after (2.4x), but most of that growth happened before launch (May to June). Comparing the 28 days either side of launch, it is 12.0 vs 12.6, so DAU has been flat since the feature shipped.
  • Usage depth is rising fast: status changes went from 47 in December to 149 in January, while DAU stayed flat. People who use the board use it more, but it is not bringing more people in per day.
  • Only about 11 of ~75 monthly users show up on a given day (DAU/MAU is roughly 15%). The opportunity is frequency among existing users.
  • 162 of 200 cards have moved at least once; 38 (19%) never moved. 286 status changes in total.

We cannot say the feature caused growth, and we cannot say it did not: the user base was already growing and levelled off right around launch.

2. Status changes by card

Most cards that move do so twice (backlog to in-progress to complete: 100 cards). Backward moves (in-progress to backlog, complete to in-progress) are only 5.6% of changes. The busiest day was 31 Jan 2019 with 17 status changes. The full per-card and per-day lists come from queries 2a and 2b.

3. Three ideas to grow daily active users

Idea 1: Stale-shipment daily digest

Hypothesis
Users have no reason to come back on a given day. 46 of the 58 cards currently In Progress (79%) have not been touched for 14+ days, and a card takes a median of ~19 days to get from In Progress to Complete. If we tell people each day which shipments are stuck, we give them a specific reason to log in, and DAU/MAU (today ~15%) will rise.

Expected impact
Planning estimate: if 1 in 5 of the ~75 monthly users logs in one extra day a week because of the digest, that is 75 x 0.2 / 7 = about +2 daily active users (+18% on the current ~11.7). It should also lift tasks completed, which supports the original 15% goal. To be validated with an A/B test (digest on vs off).

What the feature is
A short email/push each morning: 'You have 3 shipments In Progress for 7+ days', with each card linking straight to the board with that card highlighted. Users can set the threshold (7 / 14 days) or mute it.

Wireframe

Idea 2: 'Today' focus list (daily planning habit)

Hypothesis
Usage is spread evenly across every weekday and every hour of the day (Sunday is the busiest day), so there is no routine that brings users back. Priority already exists (card order) but is never used as a daily plan. If users pick a short 'Today' list each morning, opening the app becomes a daily habit and DAU rises.

Expected impact
Planning estimate: if 10 monthly users adopt the habit and add 2 active days a week each, that is 10 x 2 / 7 = about +2.9 DAU (+24%). Secondary effect: more cards moved per session. Measure with a feature-flag rollout to 50% of users and compare DAU/MAU after 4 weeks.

What the feature is
A fourth panel at the top of the board called 'Today' where users drag up to 5 cards to work on. Unfinished cards carry over to tomorrow, and a small streak counter ('4 days in a row') shows consistent use.

Wireframe

Idea 3: Assignees and activity notifications

Hypothesis
Status changes keep growing (47 in December to 149 in January, and ~9 a day by the end of the data) while DAU stays flat, so each move is currently seen only by the person who made it. If a card move notifies the people connected to that card, every move gives someone else a reason to open the app.

Expected impact
Planning estimate: at ~9 moves a day, with 1 person notified per move and 20% opening the app, that is about 1.8 extra visits a day, or roughly +1 to +2 DAU (+10-15%), and it grows as moves per day grow. Prerequisite: add a user_id column to card_change_history (today we cannot tell who moved a card), which also gives better analytics.

What the feature is
Each card can have an assignee and watchers. When a card changes lane or priority, they get an in-app notification and an optional email ('Dana moved Wiza LLC to Complete'). A simple activity feed on the board shows the latest moves.

Wireframe

Caveats. Impact figures are planning estimates built on stated assumptions, not forecasts, and should be validated with A/B tests. The launch date is inferred from the data. card_change_history has no user_id, so we cannot attribute status changes to individual users.

4. SQL queries

-- TYPE YOUR SQL QUERY BELOW
--
-- Notes
--  * Timestamps are Unix seconds, so we convert with date(x, 'unixepoch').
--  * "Launch date" = the first real status change (a row in card_change_history
--    where oldStatus IS NOT NULL). Rows with oldStatus NULL are card creation,
--    not a status change. This gives 2018-06-28.
--  * A calendar table is used so days with ZERO logins count as 0 instead of
--    silently disappearing from the average (there are 9 such days).

-- PART 1: Create a SQL query that maps out the daily average users before and after the feature change

-- 1a. Average daily active users, before vs after launch
WITH RECURSIVE
launch AS (
  SELECT date(MIN(timestamp), 'unixepoch') AS launch_date
  FROM card_change_history
  WHERE oldStatus IS NOT NULL
),
calendar(day) AS (
  SELECT date(MIN(login_timestamp), 'unixepoch') FROM login_history
  UNION ALL
  SELECT date(day, '+1 day') FROM calendar
  WHERE day < (SELECT date(MAX(login_timestamp), 'unixepoch') FROM login_history)
),
dau AS (
  SELECT calendar.day AS day, COUNT(DISTINCT l.user_id) AS active_users
  FROM calendar
  LEFT JOIN login_history l ON date(l.login_timestamp, 'unixepoch') = calendar.day
  GROUP BY calendar.day
)
SELECT CASE WHEN dau.day < launch.launch_date THEN 'before' ELSE 'after' END AS period,
       COUNT(*)                          AS days,
       ROUND(AVG(dau.active_users), 2)   AS avg_daily_active_users
FROM dau CROSS JOIN launch
GROUP BY period
ORDER BY MIN(dau.day);

-- 1b. Like-for-like check: the 28 days before launch vs the 28 days after
WITH RECURSIVE
launch AS (
  SELECT date(MIN(timestamp), 'unixepoch') AS launch_date
  FROM card_change_history
  WHERE oldStatus IS NOT NULL
),
calendar(day) AS (
  SELECT date(MIN(login_timestamp), 'unixepoch') FROM login_history
  UNION ALL
  SELECT date(day, '+1 day') FROM calendar
  WHERE day < (SELECT date(MAX(login_timestamp), 'unixepoch') FROM login_history)
),
dau AS (
  SELECT calendar.day AS day, COUNT(DISTINCT l.user_id) AS active_users
  FROM calendar
  LEFT JOIN login_history l ON date(l.login_timestamp, 'unixepoch') = calendar.day
  GROUP BY calendar.day
)
SELECT CASE WHEN dau.day < launch.launch_date THEN '28 days before' ELSE '28 days after' END AS period,
       COUNT(*)                          AS days,
       ROUND(AVG(dau.active_users), 2)   AS avg_daily_active_users
FROM dau CROSS JOIN launch
WHERE dau.day >= date(launch.launch_date, '-28 days')
  AND dau.day <  date(launch.launch_date, '+28 days')
GROUP BY period
ORDER BY MIN(dau.day);

-- 1c. Daily series used to draw the graph (one row per calendar day)
WITH RECURSIVE
launch AS (
  SELECT date(MIN(timestamp), 'unixepoch') AS launch_date
  FROM card_change_history
  WHERE oldStatus IS NOT NULL
),
calendar(day) AS (
  SELECT date(MIN(login_timestamp), 'unixepoch') FROM login_history
  UNION ALL
  SELECT date(day, '+1 day') FROM calendar
  WHERE day < (SELECT date(MAX(login_timestamp), 'unixepoch') FROM login_history)
)
SELECT calendar.day,
       COUNT(DISTINCT l.user_id) AS active_users,
       CASE WHEN calendar.day < launch.launch_date THEN 'before' ELSE 'after' END AS period
FROM calendar
CROSS JOIN launch
LEFT JOIN login_history l ON date(l.login_timestamp, 'unixepoch') = calendar.day
GROUP BY calendar.day
ORDER BY calendar.day;


-- PART 2: Create a SQL query that indicates the number of status changes by card

-- 2a. Total status changes per card (cards that never moved show 0)
SELECT c.id   AS card_id,
       c.name AS card_name,
       COUNT(h.id) AS status_changes
FROM card c
LEFT JOIN card_change_history h
       ON h.cardID = c.id
      AND h.oldStatus IS NOT NULL
      AND h.oldStatus <> h.newStatus
GROUP BY c.id, c.name
ORDER BY status_changes DESC, c.id;

-- 2b. Daily status changes by card
SELECT date(h.timestamp, 'unixepoch') AS day,
       h.cardID                       AS card_id,
       c.name                         AS card_name,
       COUNT(*)                       AS status_changes
FROM card_change_history h
JOIN card c ON c.id = h.cardID
WHERE h.oldStatus IS NOT NULL
  AND h.oldStatus <> h.newStatus
GROUP BY day, h.cardID, c.name
ORDER BY day, status_changes DESC, h.cardID;

-- 2c. How many cards had 0, 1, 2, ... status changes (used for the histogram)
SELECT status_changes, COUNT(*) AS cards
FROM (
  SELECT c.id, COUNT(h.id) AS status_changes
  FROM card c
  LEFT JOIN card_change_history h
         ON h.cardID = c.id
        AND h.oldStatus IS NOT NULL
        AND h.oldStatus <> h.newStatus
  GROUP BY c.id
)
GROUP BY status_changes
ORDER BY status_changes;
